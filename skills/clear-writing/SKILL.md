# 写清楚

写作的目标是让特定读者完成特定任务：找到答案、理解原因、做出判断、执行操作，或者知道下一步找谁。文字像不像人、够不够高级，都排在这个目标后面。

这套规则适用于中文写作、改写和审稿，也适用于英文写作中的信息组织。先保住事实和原意，再按文体安排结构，最后处理句子和措辞。不要把它当成“AI 检测器”，也不要为了显得自然而把正式文本改成口语。

它不替代作者决定观点，不替代码、配置、日志、公式和引文改字，也不把法律、合同、政策等需要权利人确认的措辞“润色”成另一种承诺。纯翻译、代码本身和接口语义不在改写范围内；它们周边的说明文字仍可按这套规则处理。

## 先判断在做什么

| 任务 | 要做的事 | 不要做的事 |
|---|---|---|
| 从零起草 | 先确认读者、目的、材料边界，再组织内容 | 用漂亮句子填补材料缺口 |
| 改写已有文本 | 先读懂全文和每段作用，再决定删、并、调、改 | 逐句替换同义词，或把改写当成翻译 |
| 审稿 | 指出结构、事实、歧义和表达问题，按严重程度排序 | 未经授权就把作者的观点改掉 |
| 随手答复 | 先回答问题，再补必要背景 | 给一句群消息套完整报告模板 |
| 正式成稿 | 完成事实核对、文体检查、受保护跨度检查，按要求运行扫描 | 把“读着顺”当成已经验证 |

材料不足时，不要把猜测写进正文。可以继续完成不依赖缺失信息的部分，在交付时单列“待确认”。原文本身有歧义时，保留歧义并说明可能的读法，不要替作者选一个意思。

## 六项质量标准

1. **对题**：回答读者真正的问题，删掉与任务无关的内容。
2. **好找**：标题、开头、目录和结论的位置符合读者的查找路径。
3. **好懂**：先给读者已知的信息，再引入新信息；句子里的动作由动词承担；一段只推进一个主要意思。
4. **可用**：读者知道要做什么、做到什么算成功、有什么限制和风险。
5. **保真**：事实、数字、命令、术语、引用、因果方向、模态、承诺和链接不被改变，也不补造。
6. **自然**：符合文体和场合，没有表演腔、空泛判断、装饰性比喻和不必要的术语堆叠。

这六项冲突时，按“保真 > 读者任务 > 文体 > 个人风格”让路。清楚不等于口语，简短不等于删掉必要信息，正式也不等于绕。

## 先立意义合同

动笔或改稿前，先把下面几类内容锁定。改完后逐项对账，原文有的要有下落，新写的要有出处。

| 项目 | 要保住什么 |
|---|---|
| 主张 | 作者到底在说什么，结论指向谁、指向什么 |
| 事实与数字 | 时间、数量、比例、版本、路径、测试结果、引用 |
| 名称与术语 | 人名、产品名、模块名、专业术语的原词和定义 |
| 关系 | 因果方向、条件、依赖、对比对象、适用范围 |
| 模态 | 已发生、预计、可能、建议、必须、尚未验证 |
| 承诺 | 谁在什么时候做什么，做到什么程度 |
| 受保护跨度 | 代码、命令、配置、日志、Prompt、公式、链接、引文 |

原文说“效果明显”，不能改成“提升了 30%”；原文说“可能”，不能改成“会”；原文说“计划”，不能改成“已经完成”。原文没有负责人、日期或原因，就在交付时提醒作者补，不要替作者编。

## 写作流程

### 1. 识别读者和使用场景

至少要能回答：

- 读者是谁，已经知道什么，最可能误解什么？
- 读者读完后要做什么决定或动作？
- 读者会在什么设备、什么时间压力下读？
- 这是学习材料、做事指南、查询资料，还是解释背景？
- 有没有用户、团队或平台的固定模板？

读者是执行者时，先给入口、前提、步骤和成功判据；读者是决策者时，先给结论、依据、取舍、风险和下一步；读者是排障者时，先给现象、影响、定位路径和临时处置。

### 2. 先搭读者的路径

开头先给读者最需要的东西：结论、请求、影响、下一步，或者一个能让人判断“这篇要不要继续读”的摘要。背景只写理解后文必需的部分。

每一节只承担一个主要问题。标题要让读者能预测下一节讲什么，避免一串看不出区别的“背景”“方案”“其他”“相关说明”。重要信息、风险、限制和下一步放在读者容易找到的位置。

模板只在用户、团队或平台明确要求时使用。模板是骨架，不是必须填满的目录；用不上的章节删掉，规则说明不要写进正文。

### 3. 先选文体的主导逻辑

长文最容易犯的错，是把教程、操作指南、参考和解释混成一篇。先判断读者此刻要完成什么，再决定以哪种逻辑为主：

| 读者要完成的事 | 主导文体 | 先给什么 | 不要混入什么 |
|---|---|---|---|
| 第一次学会一个概念或技能 | 教程 | 一个可完成的学习路径和练习 | 完整参数表和所有边界 |
| 完成一个具体任务 | 操作指南 | 前提、入口、步骤、成功确认 | 长篇原理和无关背景 |
| 查一个字段、参数或返回值 | 参考 | 稳定的结构、默认值、范围、示例 | 教学叙事和未经证实的建议 |
| 理解为什么这样设计 | 解释 | 问题、心智模型、机制、取舍、边界 | 逐步操作和字段清单 |

一篇长文可以包含多种内容，但要明确哪一种是主线，其他内容只做必要的跳转或补充。用户或团队已有模板时，模板优先；模板和读者任务冲突时，指出冲突，不要偷偷改结构。

### 4. 按文体组织内容

| 文体 | 读者最想先看到 | 主体应包含 |
|---|---|---|
| 聊天、邮件、群消息 | 答案或请求 | 必要背景、下一步、需要对方做什么 |
| 周报、状态同步 | 结果和风险 | 已完成、证据、阻塞、下一步、需要谁支持 |
| 技术方案、决策文档 | 推荐结论 | 问题、目标与非目标、选项与取舍、实施、风险、验证 |
| 事故复盘 | 影响和当前状态 | 事实时间线、根因与促成因素、处置、防止再发、未确认项 |
| 操作文档 | 适用任务和前提 | 角色、入口、一步一个动作、成功确认、异常处理 |
| Reference | 查什么、在哪查 | 稳定的字段、参数、返回值、限制、示例 |
| Explanation | 为什么 | 问题、心智模型、机制、例子、边界 |
| README | 这是什么、怎么开始 | 用途、安装、最小示例、配置、排障、链接 |
| 公开通知 | 谁、何时、做什么 | 影响范围、截止时间、所需动作、依据或联系方式 |
| 评审、纪要 | 决定了什么 | 结论、分歧、行动项、负责人、截止时间、未决问题 |

更细的结构、信息层级和排版选择见 [document-design.md](references/document-design.md)。技术正文的术语、证据、标识符和图见 [technical-writing.md](references/technical-writing.md)。操作手册的步骤写法、团队模板映射和异常处理见 [operation-docs.md](references/operation-docs.md)。

### 5. 写段落和句子

段落先给本段要成立的判断，再给事实、机制、取舍和影响。一个段落只推进一个主要意思；确实需要换话题时另起一段。

句子遵守几条读者期待：

- 把承接前文的旧信息放在句首，把要强调的新信息放在句末。
- 主语和动词尽量靠近，别让长修饰语把两者拆开。
- 把动作写回动词。能说“验证配置”，就不说“对配置进行验证”。
- 先给语境，再引入新概念。读者还不知道“它”指什么时，不要用“它”开头。
- 具体名词优先。抽象判断要有材料中的事实支撑。
- 一句话可以长，但要让读者知道主要动作和结论落在哪里。
- 并列只在真正并列时使用列表或表格。有因果、有取舍、有机制的分析写成段落。
- 术语第一次出现时解释一次，后文保持同一种叫法。

这些是读者期待，不是语法判决。为了强调、节奏或文体效果，可以有意违反；先保证大多数句子让读者省力。

### 6. 诊断“AI 味”

按“全篇 → 段落 → 句子 → 词语”的顺序检查，不要一上来逐句润色。重点看：

- 万能动词加抽象名词，例如“进行分析”“作出贡献”“实现提升”。
- 连续套用“通过……实现……从而……”，一句话塞进多个动作和结果。
- 空泛的重要性判断、假权威和无来源的“研究表明”。
- 装饰性比喻、宏大词汇、为了显得深刻而造的词。
- 每段都“铺垫、展开、小结”，或摘要、正文、结尾反复说同一件事。
- 同义反复、指代不清、同义词循环。
- 所有内容都被拆成加粗短语、列表和小标题，段落失去论证。
- 正文里交代写作过程、材料局限或“以上仅依据……”式免责话。
- 机械对仗、过量三段式、用数量给内容贴标签。

这些是编辑信号，不是自动判决。技术术语、法律条款、正式敬语、必要的被动句、真正的三项并列、编号步骤和有意使用的破折号，都可能是正确的。判断标准是读者是否因此更难理解、判断或执行。详细症状、误报边界和改法见 [style-diagnostics.md](references/style-diagnostics.md)。

### 7. 验证再交付

至少做五类检查：

1. **事实对账**：意义合同里的每一项，在成稿中都有下落；成稿中的每个具体信息，都能在材料里找到出处。
2. **读者任务自检**：一个不了解背景的读者，能否回答“发生了什么、为什么、我该做什么、怎么知道成功、还有什么不确定”。
3. **歧义测试**：原文有歧义时，改写有没有替作者偷偷选了一种读法。
4. **文体测试**：正式场合是否保留了应有的敬语、气势和分寸；随手答复是否被套上了不必要的模板。
5. **真实读者测试**：条件允许时，找目标读者做复述、任务或对比测试；没有做就在交付说明里写“未做读者测试”，不要把作者自读或脚本扫描说成读者验证。

对要写回飞书、对外发布或进入长期文档库的中文成稿，应运行：

```bash
python3 "$HOME/.agents/skills/clear-writing/scripts/clarity_check.py" <文件>
```

脚本只标出可复核的字面问题和编辑线索，不判断作者意图，也不输出“AI 分数”。`--strict` 只把中文正文中的半角标点等字面项作为失败条件；其他提示仍需人判断。代码块、行内代码、URL、HTML 注释、YAML frontmatter、数字和英文术语会被屏蔽；未闭合的代码围栏或 HTML 注释会以退出码 2 报错，不静默跳过。

如果 Skill 装在别的目录，把命令中的路径换成实际安装位置。

写回飞书或对外发布时，记录命中数、逐条处理结果和必要的豁免理由。随手答复不必跑脚本，按下面的自检清单心里过一遍即可。

交付时只说明实际做过什么。结构检查、脚本扫描、真实读者测试和发布验收是不同层次的证据，不要互相替代。

## 编辑力度

- **轻改**：只改词和局部句，不动段落和结构。适合原文总体清楚，只需去掉最刺眼的毛病。
- **标准**：可以改句、并段、删冗余，不主动重排章节。适合大多数改稿请求。
- **结构改**：只有用户明确要求，或原文明显无法完成读者任务时才动。改动后说明动了哪一层、为什么。

每改一处，都要能说出它治的是哪个具体问题：事实不清、指代不明、句子憋气、段落偏题、标题不能预测内容，等等。说不出来，就放回原样。原文清楚得体的句子，保留也是正常结果。

## 保真红线

- 不新增原文没有的数字、日期、负责人、原因、场景、身份或承诺。
- 不改变因果方向、条件、适用范围、比较对象和不确定性。
- 不把专业术语替换成看似通俗但定义不同的词。
- 不改代码、命令、配置、日志、公式、引文和链接的内容。
- 不把“建议”“计划”“预计”“可能”写成“必须”“已经”“一定”。
- 不替作者删除他明确要求保留的限定、免责声明或法律措辞。
- 不用“更自然”为理由，改动合同、法规、政策和对外承诺的实际含义。

改写时如果原文本身模糊，保留模糊度，并在正文外单列待确认项。不要用“以上仅依据……”这类话污染正文；需要提醒作者时，放在交付说明里。

## 中文写作的额外检查

- 中文正文默认使用全角标点；代码、URL、版本号、英文原文和数字格式按原样保留。
- 少用“进行、作出、实现、完成、开展、予以”这类万能动词，先找真正的动作。
- 少用“通过……实现……从而……”把多个动作压成一条长链；需要时拆开，写清谁做了什么、结果是什么。
- 少用“有关、关于、由于、作为”开头的空架子；直接写主语和动作。
- 长定语、连续“的”、过量被动和从句堆叠，只有在确实需要精确限定时才保留。
- 已经归化的欧化表达不必一律清除。判断标准是中文能否说得同样准确、同样有劲；能，就改成中文习惯；不能，就保留必要结构。
- 动词和形容词要配得上主语。问一句“这个动作或状态，这个东西真做得出来吗”；配不上就换词，不要为了有力硬套。
- 姿态平视。不写“很多人没搞懂，而我早就看透了”这类抬高自己的话，也不写“好问题”“希望这对您有帮助”这类讨好垫话。
- 正式公文、客服话术、致辞、招聘文案中的敬语和气势是文体功能，不当废话删。

## 交付前自检

- [ ] 能用一句话说清读者是谁、读完后要做什么。
- [ ] 开头给了读者最需要的信息，背景没有抢在结论前面。
- [ ] 每一节只回答一个主要问题，标题能预测内容。
- [ ] 重要信息、风险、限制和下一步都在容易找到的位置。
- [ ] 段落有明确主旨，句子的旧信息和新信息顺序合理。
- [ ] 动作主要落在动词上，抽象判断有事实支撑。
- [ ] 术语统一，第一次出现有解释，标识符没有挤占正文。
- [ ] 列表和表格只用于真正并列或查询的内容。
- [ ] AI 味检查发现的问题都有具体处理理由，没有为了“像人”新增信息。
- [ ] 事实、数字、命令、术语、模态、承诺和链接逐项对过。
- [ ] 正式文本没有被强行口语化，随手答复没有被过度包装。
- [ ] 写回飞书或对外发布时运行了扫描，并记录了命中数、处理结果和豁免理由。
- [ ] 区分了字面问题、编辑建议、作者自检和真实读者验证；没做读者测试就明确说明。
