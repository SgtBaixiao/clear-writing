# 技术写作

技术文档的第一要求是可核对，第二要求是可理解。文字要让人看出哪些是代码事实、哪些是测试结果、哪些是作者推断。

## 正文写业务含义，标识符放到可查的位置

正文的主语和动作应该由读者能理解的概念承担。变量名、函数名、字段名、枚举值、文件路径、命令行参数，优先放进表格、代码块、图或索引。

不绝对禁止标识符出现在正文。读者本身就用这个标识符工作，或者标识符就是讨论对象时，可以直接写。判断标准是：遮住标识符后，读者还能不能知道这句话在说什么。如果不能，说明正文缺了业务含义。

示例：

不推荐：

> `BaseImageAgent` 读取 `trajectory.jsonl`，调用 `resolve_image`，把结果写入 `seed/env.yaml`。

更清楚：

> 环境准备器读取录制轨迹，先判断基础镜像，再把结果写入环境规格文件。具体入口和字段见代码索引。

## 术语

- 同一概念全文只用一个叫法。
- 第一次出现时，用一句读者能懂的话解释；有通用中文名就用中文名，没有就保留原词。
- 不要为了“通俗”把有确切定义的术语换成近义词。例如“重构”不是“重写”，“幂等”不是“重复执行不会报错”。
- 内部缩写超过三个，或同名异义容易混淆时，加一张术语表。
- 术语表解释“它是什么、读者为什么需要知道”，不要只把英文翻译一遍。

## 事实、推断和未确认项

把三类内容分开：

| 类型 | 例子 | 写法 |
|---|---|---|
| 事实 | 代码在某个分支的行为、测试输出、日志、接口定义 | 直接陈述，给出版本、路径或时间 |
| 推断 | 设计意图、根因猜测、性能影响、方案取舍 | 标明“推断”或放入单独小节 |
| 未确认 | 只有口头来源、无法复现、未在目标环境验证 | 单列“未确认事项”，不写成结论 |

证据强度要和措辞匹配。代码里明确写死的行为，不必加“可能”；只跑过一次的测试，不要说“稳定”；没有做过容量测试，不要写“可以支撑高并发”。

## 溯源

关键事实尽量给读者一条可追查的路径：

- 代码位置：文件、函数、行号或 commit。
- 数据：来源、口径、统计时间、样本范围。
- 测试：环境、版本、命令、结果、失败条件。
- 外部资料：作者、标题、版本或日期、链接。

正文不必被长括号打断。可以把定位集中到表格的“出处”列、脚注或文末索引。

## 结构

技术方案和设计文档：

1. 问题、现状和影响。
2. 目标与非目标。
3. 约束和前置条件。
4. 方案全貌。
5. 关键机制和取舍。
6. 迁移、回滚和兼容性。
7. 风险、验证和指标。
8. 待确认项。

代码走读：

1. 这份代码解决什么问题。
2. 入口和数据流。
3. 模块职责和依赖关系。
4. 关键设计及原因。
5. 失败路径和边界。
6. 可改进点和风险。

实验报告：

1. 问题和假设。
2. 实验设置、变量和基线。
3. 结果。
4. 结果解释和竞争解释。
5. 适用条件、误差和未验证部分。

## 长文档

长文档不一定要放“结论速览”，但如果读者需要先判断要不要读，开头可以给 5–10 条判断，而不是目录复述。每条说一个结论和一条关键依据。

超过四屏、且读者会跳读的文档，可以加：

- 术语表。
- 目录或问题索引。
- 事实与推断的说明。
- 代码或资料索引。
- 未确认事项。

这些是导航工具，不是每篇文档的固定章节。短文档加这些只会增加负担。

结论速览里的每条都应该是判断，不是“本文分为几部分”的目录复述。术语表只解释读者第一次看到、不查资料就理解不了的词；事实、作者推断和未确认事项要分开写。重点框只承载读者漏掉会出事的风险、边界或关键原则，不在正文、框和小结里重复同一句话。

## 表格和代码

表格适合参数、字段、选项、版本、责任和对比。列不要过多，第一列放查找键。长文本单元格通常意味着应该改成小节。

表格尽量不超过五列；超过时拆表或删列。表格前用一句话说明怎么读，表后不要逐行复述。单元格里塞进三行以上文字时，改成小节或列表。

代码块、命令、配置、日志、Prompt 原文和接口定义按原样保留。只改它们周围的解释、标题和排版。不要把代码里的换行、缩进、大小写或标点“顺手优化”。

## 图

图用来表达文字很难一眼看清的关系：流程、依赖、分层、状态变化、时间顺序。画之前先确定这张图回答哪一个问题；一张图只回答一个主要问题，问题多了就拆图。

- 流程图写清起点、终点、判断分支和回流；箭头方向要能顺着读，分支条件写在连线旁。
- 架构图写清边界、外部依赖、调用方向，以及同步还是异步；不要把没有关系的模块画在一起。
- 状态图写清状态、触发事件和迁移条件；不要只画一排状态框，不画怎么变化。
- 数据图写清坐标轴、单位、样本范围、时间口径和基线；有误差或不确定性就标出来。
- 示意图和图注要说明“这是结构示意，不是真实数据”；数据图要说明数据来源和统计时间。

图注不是重复标题，而是告诉读者“这张图里最该看什么”。图里的文字要能独立读，不要小到必须放大；不要把正文整段搬进图里。装饰性图标、渐变和阴影不能代替结构信息。

同一篇文档的多张图要用同一套颜色、形状和箭头语义；颜色只表达固定含义，不做装饰。总览图可以在底部放一条结论，写这张图支持的判断，不要复述图里的标签。图里出现多个维度时拆图，不把时序、数据量和依赖关系硬塞进一张图。

## Reference 文档

Reference 回答“有什么、怎么用、返回什么、有什么限制”，不负责教学。写法：

- 结构尽量对应系统本身的结构。
- 字段、参数、返回值和异常保持一致。
- 说明默认值、单位、范围、是否必填和版本差异。
- 示例最小化，不把教程塞进参考页。
- 不混入未经证实的建议。

## Explanation 文档

Explanation 回答“为什么这样设计”。可以先给一个心智模型，再讲机制、取舍、例子和边界。允许作者观点，但要和事实分开。

不要把 Explanation 写成操作步骤，也不要把 Tutorial 写成参考手册。四类文档混在一起，读者会不知道当前该读什么。

## 技术写作自检

- [ ] 不熟悉代码的工程师能讲清系统在做什么。
- [ ] 正文里的标识符没有代替业务含义。
- [ ] 术语第一次出现有解释，全文叫法一致。
- [ ] 代码事实、测试结果、作者推断和未确认项分得开。
- [ ] 关键结论有来源、版本或复现条件。
- [ ] 性能、容量、稳定性等结论没有超出实际测试范围。
- [ ] 代码、命令、配置和引文保持原样。
- [ ] 长文档的导航工具确实帮助查找，而不是重复正文。
