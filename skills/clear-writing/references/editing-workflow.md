# 改稿流程

改稿不是把原文换成另一种腔调。先读懂原文要做什么，再决定改哪一层。

## 一、读全文

先通读，不急着改字。记录：

- 读者是谁，读完后要做什么。
- 全文的主张和结构。
- 每段承担什么作用。
- 哪些事实、数字、命令、术语和链接不能动。
- 哪些地方原文本身有歧义或缺口。

如果文章结构本身无法完成读者任务，先提出结构调整建议。用户没有授权大改时，不要擅自重排章节。

## 二、建意义合同

| 项目 | 原文中的内容 | 成稿中的下落 |
|---|---|---|
| 主张 | | |
| 关键事实 | | |
| 数字和单位 | | |
| 专名和术语 | | |
| 因果和条件 | | |
| 模态 | | |
| 承诺和时间 | | |
| 受保护跨度 | | |

合同是双向的：原文的每条信息在成稿里有下落，成稿的每条具体信息在原文或材料里有出处。

## 三、选力度

### 轻改

只换词、顺局部句，不拆段、不动结构。适合原文总体清楚，只需要去掉最刺眼的毛病。整段该删时，列建议，不直接删。

### 标准

默认档。可以改句、并段、删冗余、调整段内顺序，不主动重排章节。发现整段重复或偏题，可以删，但要在交付说明里讲清。

### 结构改

只有用户明确说“大改”“重写”“调结构”，或原文明显无法完成读者任务时才动。可以合并、拆分、重排章节和大段删改。结构改动后说明动了哪一层、为什么。

## 四、按层修改

### 结构层

- 开头是否先给读者需要的东西。
- 每节是否只回答一个主要问题。
- 标题是否能预测内容。
- 同一件事是否被拆散或重复。
- 重要风险、限制和下一步是否在可找到的位置。

### 段落层

- 每段是否有明确中心。
- 段与段之间是否有承接。
- 论证是否只有判断没有证据，或只有材料没有解释。
- 列表和表格是否替代了本该写清的因果和取舍。

### 句子层

- 主语和动词是否靠近。
- 动作是否落在动词上。
- 旧信息是否在前，新信息是否在后。
- 长句是否有自然停顿和清楚的结论。
- 指代是否唯一。
- 是否连续使用同一种句式。

### 词语层

- 是否有空泛判断、假权威、装饰性比喻和生造词。
- 术语是否统一，第一次出现是否解释。
- 中英混排是否影响理解。
- 正式文体的敬语和分寸是否保留。

## 五、处理原文缺口

原文缺数字、日期、原因、负责人或入口时：

- 不要补。
- 保留原文的模糊度。
- 在正文外单列“待确认”。

原文有歧义时：

- 上下文能确定，按上下文改。
- 不能确定，只顺语序，不替作者选读法。
- 交付时说明可能的读法。

原文本身有“预计”“可能”“尚未验证”等限定，照留。不要为了句子利落把限定删掉。

## 用户指定风格

用户给出样例、要求“按我的风格写”，或明确说明偏好时，先看可观察的特征：称呼、句长、段落节奏、口语程度、术语密度、常用句式和情绪强度。只在这些表达维度内靠拢，不要从样例推断作者的身份、经历、立场或事实。

样例里的具体事实、数字、案例和承诺不能搬进新稿。风格和保真、场合冲突时，先保事实和文体；用户要求口语化，但文本是对外公函，仍按公函的分寸写。

## 六、回读

至少做三遍：

1. **事实回读**：对照意义合同，逐项核对数字、术语、因果、模态和承诺。
2. **表达回读**：以不了解背景的读者身份读，看哪里需要猜、哪里会误解。
3. **节奏回读**：出声读长句和关键段，找憋气、重复和没有落点的句子。

长文或公开稿再加一遍“只读标题和每段第一句”，看能否还原文章主线。

### 节奏检查

念出声是最直接的检查。一口气顶到底、中途倒不上气，就补逗号、断句或拆句；连续几句长度和开头都一样，就调整一处；段末总是“从而”“进而”“为……提供支撑”，就看看这句话有没有实际落点。

节奏管的是句子顺不顺、能不能喘上气，不管够不够口语。长句本身不是病，病在从头到尾没有一个停顿。正式文本可以长，技术限定可以长，但要让读者知道主要动作和结论落在哪里。

### 受保护跨度

下面这些内容按原样保留，不改字、不改标点、不改换行和大小写：

- 代码、命令、配置、日志、报错、Prompt 原文。
- 数字、单位、比例、版本号、日期、时间、金额。
- 人名、产品名、模块名、字段名、枚举值、文件路径、URL。
- 引文、法规条款、合同措辞、用户明确要求保留的原话。

受保护跨度里如果确实有错，标出来请作者确认，不要顺手改。代码块和行内代码的标点不属于中文正文的标点检查范围。

按文体还要多保护一层：

| 文体 | 额外保护 |
|---|---|
| PRD、技术方案、API 文档 | 接口签名、参数名、返回结构、错误码、状态名、协议名、性能指标 |
| 事故复盘 | 时间戳、告警名、指标名、责任人、变更 ID、因果链方向、影响范围 |
| 周报、状态同步 | 项目名、里程碑、截止时间、进度数字、分工归属 |
| 学术、严肃技术文 | 公式、符号、定理名、引理编号、作者、年份、期刊、DOI |
| 法律、合同、政策 | 权利义务、限定条件和责任措辞；没有权利人确认，不擅自改写 |

## 七、读者测试

自己读顺不等于读者能懂。条件允许时，在定稿前找目标读者做一次测试；风险越高、读者越陌生，越值得做。

| 方法 | 怎么做 | 能发现什么 |
|---|---|---|
| 复述测试 | 让读者读完用自己的话复述主要结论、依据和下一步 | 读者是否抓住了重点，哪里被误解 |
| 任务测试 | 给读者一个具体任务，例如“找到截止时间”“按文档完成这一步”，观察他去哪找、在哪里停 | 信息是否好找，步骤是否可执行，成功判据是否清楚 |
| 对比测试 | 让另一组读者读修改前或另一版，完成同一任务 | 修改是否真的减少了查找、误解或操作错误 |

测试时只记录读者实际说了什么、做了什么，不替他解释。样本量按风险和资源决定；少量读者的反馈能发现明显问题，但不能当成统计证明。至少留出一轮修改时间，重要文档尽量做两轮。没有做读者测试时，在交付说明里写“未做读者测试”，不要把作者自读、脚本扫描或模型检查说成读者验证。

## 八、脚本扫描

需要时运行：

```bash
python3 "$HOME/.agents/skills/clear-writing/scripts/clarity_check.py" <文件>
```

如果 Skill 装在别的目录，把命令中的路径换成实际安装位置。

脚本输出三类信息：

- 字面问题：例如中文正文里的半角标点。
- 编辑线索：例如万能动词、长句、机械编号、空泛元话语。
- 汇总：各类命中数量。

使用原则：

- 先看全篇和段落，再用脚本找漏。
- 字面问题按文体和项目规范处理；代码、URL、数字和英文原文不误改。
- 编辑线索逐条判断，不自动替换。
- 脚本零命中不能证明文章清楚，脚本命中也不能证明文章有 AI 味。

## 九、交付说明

不是每次改稿都要写报告。以下情况建议给简短说明：

- 用户要求审稿或改稿。
- 做了结构调整。
- 原文有明显材料缺口或歧义。
- 运行了扫描，需要记录结果。

说明只写：

- 改了哪一层。
- 主要改了什么，为什么。
- 哪些事实或结构没动。
- 哪些信息需要作者补。
- 做了哪些验证，哪些没做。

不要把“以上仅依据你提供的材料”“未做额外核验”写进正文。正文要能直接交给最终读者；给作者的提醒放在正文外。

## 十、停止条件

出现下面任一情况就停：

- 核心事实无法确认，继续改会改变原意。
- 原文歧义无法靠上下文解决，需要作者选择。
- 结构调整超出用户授权。
- 法律、合同、政策措辞需要权利人确认。
- 读者任务本身不清楚，继续润色只会把错误说得更顺。

停止不是失败。把已确认的部分交付，把阻塞点和恢复条件写清，比编一个完整答案可靠。
