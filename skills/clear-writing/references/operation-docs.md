# 操作文档

操作文档服务一个明确任务：让特定角色在特定前提下，按步骤完成操作，并知道怎样确认成功。它和解释文档、参考文档不是一回事。

## 先收集信息

写之前确认：

- 操作对象是什么。
- 谁有权限、谁应该执行。
- 什么时候需要做，什么时候不该做。
- 入口在哪里，前置条件是什么。
- 有哪些全局限制和单步限制。
- 做完后怎样判断成功。
- 常见失败是什么，失败后怎么恢复。

材料里没有的入口、按钮名、字段名和报错，不要猜。宁可写“待确认”，也不要把“点击设置”写成“点击高级设置”。

## 推荐结构

短操作可以只用：目的、前提、步骤、成功确认。

复杂操作再按需增加：

1. 一句话说明这个文档帮谁完成什么。
2. 适用范围和全局限制。
3. 全局前提条件。
4. 业务流程或操作流程，仅在读者需要先建立整体认识时使用。
5. 具体操作任务。
6. 成功确认。
7. 异常处理。
8. 后续操作或相关文档。

不要为了套模板保留空章节。模板要求“基本概念”时，只在确有理解门槛高的术语时保留；状态枚举和普通字段不需要单独解释。

## 团队模板映射

如果团队使用固定的操作文档模板，可以按下面的映射落位。模板是骨架，不是必须填满的目录；没有内容的可选章节直接删掉，章节的规则说明不要写进正文。

| 模板章节 | 写什么 | 判断 |
|---|---|---|
| 标题 | 能概括全文的文档标题；具体操作用“动词 + 对象” | 标题最多四级，不跨级，不写标点，避免孤立编号 |
| 短描述 | 一句话说清 what / who / when / why | 不用标题格式，不复述标题，角色要具体 |
| 基本概念 | 第一次看到、不查资料就理解不了的术语 | 状态枚举、自解释字段和普通配置项不放这里 |
| 业务流程 | 涉及上下游关联操作时，用流程图给出全貌 | 没有上下游关系就删掉 |
| 操作流程 | 一个主流程包含多个子操作时，用流程图给出路径 | 没有多个子节点就删掉 |
| 使用限制 | 影响整个功能是否可用的环境、范围、版本、配额、不可逆风险 | 单个字段或单步限制放到对应步骤旁 |
| 前提条件 | 不满足就无法开始所有操作的权限、资源、前置动作 | 登录通常不算前提；单任务前提放到该任务开头 |
| 操作角色与入口 | 具体角色，以及前端页面入口 | 不写“具备权限的用户”；入口写页面路径 |
| Verb + Task | 每个具体操作一节：适用场景、局部限制、前提、步骤、成功确认 | 一步一个动作，写清位置、动作、对象、结果 |
| 后续操作 | 成功后明确的下一步 | 没有就删掉 |
| 了解更多 | 相关文档、FAQ、排查手册、权限申请入口、API 文档 | 没有就删掉 |

有业务流程或操作流程时，把流程节点涉及的操作聚合到“xxx 流程”目录下，不要把一个主流程拆成互不相干的扁平任务；流程之外的操作聚合到“其他操作”。没有流程时，才按具体操作扁平组织。聚合目录用名词短语，具体操作用“动词 + 对象”，两种命名不要混。

## 标题

具体操作标题用“动词 + 对象”，例如“配置回调地址”“导出访问日志”。文档总标题可以概括整个任务集合，不必强行用动词。

聚合目录可以用名词短语，例如“发布流程”“其他操作”。同一层级的标题保持同一种结构。

## 前提和限制

把全局和局部分开：

| 类型 | 放在哪里 | 判断 |
|---|---|---|
| 全局前提 | 文档前部 | 不满足它，所有操作都无法开始 |
| 全局限制 | 文档前部 | 影响整个功能是否适用，例如环境、版本、配额、租户范围 |
| 单任务前提 | 对应任务开头 | 只影响这个任务 |
| 单步限制 | 对应步骤旁 | 只影响这一动作，例如字段格式、状态要求 |

“已登录平台”通常不算前提条件，除非登录本身是读者容易漏掉的关键步骤。登录后的页面入口要写清。

## 步骤

一步只写一个主要动作。每步尽量包含：

**位置 → 动作 → 对象 → 结果**

示例：

> 在“任务列表”页面，单击目标任务的“编辑”，进入编辑页面。

优先使用明确动词：打开、选择、输入、上传、确认、保存、复制、删除。不要用“处理一下”“配置好”“完成相关操作”代替具体动作。

条件分支写清判断条件：

> 如果实例状态是“运行中”，先单击“停止”；如果已经是“已停止”，直接进入下一步。

不要把多个动作压成一个步骤：

> 不推荐：打开设置，选择网络，填写地址，保存后重启。

更清楚：

1. 打开“设置”。
2. 选择“网络”。
3. 在“服务地址”中填写地址。
4. 单击“保存”。
5. 重启服务。

## 警告和风险

会造成数据丢失、不可逆变更、权限扩大、服务中断或费用增加的操作，警告放在动作之前。

写清三件事：

- 什么操作有风险。
- 会发生什么后果。
- 执行前要做什么确认或备份。

不要把警告写成一个泛泛的“请注意操作风险”。读者需要知道具体风险和规避动作。

## 配置项和字段

配置项用表格：

| 配置项 | 必填 | 说明 |
|---|---|---|
| 名称 | 是 | 长度限制、允许字符、是否可重复 |
| 地址 | 是 | 协议、格式、示例 |
| 超时 | 否 | 单位、默认值、取值范围 |

字段说明要写读者做决定需要的信息，不要只复述字段名。列表页已经能看到的筛选项，不必在正文再解释一遍。

## 成功确认

最后一步必须让读者知道怎样确认操作成功。成功判据要可观察：

- 页面状态变成什么。
- 哪条记录出现或消失。
- 哪个接口返回什么。
- 哪项指标在什么时间范围内变化。
- 哪个日志或事件出现。

“确认配置生效”不够具体。要写“刷新实例列表，状态从‘变更中’变为‘运行中’”。

## 异常处理

异常紧跟相关步骤，不要集中到文末让读者来回跳。

多个错误用表格：

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 按钮不可见 | 角色权限不足 | 联系管理员开通指定角色 |
| 保存报错 | 必填项缺失或格式不符 | 按字段表检查后重试 |

单个错误可以用一段说明。不要把所有异常都归因于“网络问题”或“配置错误”；没有证据就写“原因待确认”。

## 图和截图

有上下游依赖或多个子任务时，可以用流程图帮读者建立全貌。流程简单、线性步骤清楚时，不为了满足模板而画图。

团队模板要求业务流程图或操作流程图时，Markdown 文档优先用 mermaid；飞书文档用画板或流程图组件。图要能看出起点、分支条件和终点，不能用一段文字假装成流程图。

截图只在能减少定位成本时使用。截图里的按钮、菜单和字段要与正文一致；无法确认界面时不要编造截图说明。

## 验证

能执行的操作，尽量实际走一遍；不能执行时，明确这是“未在目标环境验证”的稿子。检查：

- 每一步是否有明确动作和结果。
- 入口、按钮、字段和报错是否与真实界面一致。
- 前提、限制和警告是否放在正确位置。
- 最后是否有可观察的成功判据。
- 异常处理是否贴近对应步骤。
- 模板中的可选章节是否按需删除。

操作文档的价值在于读者能做成事，不在于章节齐全。
